### 第一關到底如何擋？

- **G0 採集前置：** 按照指定截稿窗抓來源、排除無效日期／原創網址／不夠 50 字的來源重點、排除不適合的候選、去重、檢查獨特事件與出版者／題材多樣性。原始 URL 423 筆並不等於 423 則具報導內容的新聞。
- **G1 選題前置：** 有 20 個候選事件仍不足以過關。必須在任何產稿前，確實分類成 10–12 主新聞與 10–12 非同一事件的補充快訊；舊程式 `canonical_issue(max_items=12)` 必然被 G1 拒絕，直到第二輪解決容量與分類。這是故意的**先擋後修**，不是假綠燈。
- **阻擋輸出：** `P2_V3_CONTENT_HOLD.json` 只能含數量、缺口與原因，不得包含「看似成品」的日報網頁或 EPUB；Python / GitHub 成功只表示診斷完成，不是編輯合格。
- **測試例外：** 單元測試可產出有 `FIXTURE_ONLY_NOT_FOR_OWNER` 身份的假資料，僅供 CI 迴歸，不得提供業主閱讀或宣稱正式新聞品質。

## 永遠不可以為了補數量做的事情

1. 單一新聞拆成多則、不同網站轉貼同一新聞算兩則、拿舊新聞混成今日頭條。
2. 以缺乏可取得全文為理由補造細節、日期、機率、經濟數字、因果或不存在的官方結論。
3. 用數百筆 RSS、source URL 個數、Gemini 生成段落數、版面文字長度取代可核對新聞篇數。
4. 以達到字數作為免人工檢驗的 PASS；還需真人閱讀與編輯證據。
5. 不合格版 Essential/Deep、歷史演示稿反覆要求業主評價；不應重複消耗時間。
6. 自動新增付費來源、增加有成本的 Gemini 用量、啟動 Pages/LINE、修改原定六次暫時快照排程、觸及 Zinc 原 repo。
7. 將非 P2 正式新聞證據或 EPUBCheck 技術成功冒稱 P2 / P3 / P4 或發刊合格。
